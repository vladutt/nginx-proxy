# nginx-proxy

A version-controlled nginx reverse proxy for one Ubuntu server with Docker.
Each project on the server gets its own subdomain (`app.<DOMAIN>` → a
container or a local port). HTTPS uses **one wildcard certificate**
(`<DOMAIN>` + `*.<DOMAIN>`) from Let's Encrypt via **Cloudflare DNS-01**.

Everything is driven by `.env`; no domain or project is hard-coded.

## Layout

| Path | Purpose |
|------|---------|
| `docker-compose.yml` | `nginx` + `certbot` (dns-cloudflare) services, external `proxy` network |
| `nginx/nginx.conf` | Global settings (gzip, timeouts, log format, `server_tokens off`, Cloudflare real IP) |
| `nginx/snippets/` | Shared includes: `proxy-headers`, `ssl-cert` (wildcard paths), `ssl-params`, `security-headers`, `rate-limit`, `websocket` (opt-in), `cloudflare-realip` |
| `nginx/conf.d/00-default.conf` | Catch-all: unknown hosts get `444`, unknown TLS SNI is rejected |
| `nginx/conf.d/<sub>.<DOMAIN>.conf` | One file per site (generated by `add-site.sh`) |
| `templates/site.conf.template` | Site template used by `add-site.sh` |
| `examples/app.example.conf` | Documentation-only example; **not** loaded by nginx |
| `secrets/cloudflare.ini.example` | Placeholder for the Cloudflare API token |
| `scripts/` | `init-cert.sh`, `add-site.sh`, `remove-site.sh`, `update-cloudflare-ips.sh` |

## Prerequisites

- Ubuntu server with Docker and the Compose plugin; ports 80 and 443 open.
- DNS for the domain on **Cloudflare**, with `<DOMAIN>` and `*.<DOMAIN>`
  records pointing at the server (orange or grey cloud, see below).
- A Cloudflare API token with **only** `Zone → DNS → Edit` on that one zone.
  No other permissions are needed.

## First setup (order matters)

```sh
# 1. network shared with the proxied containers (name must match PROXY_NETWORK)
docker network create proxy

# 2. configuration and the Cloudflare token
cp .env.example .env                                   # set DOMAIN, LETSENCRYPT_EMAIL
cp secrets/cloudflare.ini.example secrets/cloudflare.ini
$EDITOR secrets/cloudflare.ini                         # paste the token
chmod 600 secrets/cloudflare.ini

# 3. issue the wildcard certificate (DNS-01, takes ~1 minute)
scripts/init-cert.sh

# 4. start
docker compose up -d
```

`.env` and `secrets/cloudflare.ini` are git-ignored; never commit them. Set
`LETSENCRYPT_STAGING=1` first to try the flow against the staging CA (untrusted
certs, no rate limits); when switching to production re-run
`scripts/init-cert.sh --force-renewal`. `init-cert.sh` passes extra arguments
to certbot, so `scripts/init-cert.sh --dry-run` is also available.

`init-cert.sh` wraps:

```sh
docker compose run --rm --entrypoint certbot certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials /run/secrets/cloudflare.ini \
  --cert-name wildcard -d <DOMAIN> -d '*.<DOMAIN>' ...
```

The certificate lineage is always named `wildcard`, so the nginx config
(`snippets/ssl-cert.conf`) never contains the domain. With no sites,
nginx starts fine even before a certificate exists.

## Adding a project in 3 steps

nginx reaches projects through their **published host ports** via
`host.docker.internal:<port>`. Projects need no shared network, so they can be
stopped, rebuilt and recreated (`docker compose down && up`) with nothing to
reconnect and no nginx reload.

1. **Publish a port on the Docker bridge IP** in the project's own compose
   file (not on all interfaces):
   ```yaml
   ports:
     - "172.17.0.1:8000:8080"     # <bridge-ip>:<host-port>:<container-port>
   ```
   `host.docker.internal` resolves (`host-gateway`) to the docker0 bridge
   address, so that is where nginx connects. Find yours with
   `docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}'`
   (usually `172.17.0.1`; use the value it prints). A port bound to the bridge
   IP is **not** reachable on the server's public or LAN addresses.
2. **Generate the site:**
   ```sh
   scripts/add-site.sh app                      # pick the container; uses its published port
   scripts/add-site.sh app host.docker.internal:8000   # explicit (localhost:8000 is rewritten)
   scripts/add-site.sh app host.docker.internal:8000 --ws   # WebSocket app
   ```
   The picker lists running containers and defaults to their published host
   port (you choose if there are several). If a port is published on all
   interfaces (`0.0.0.0`/`::`) it warns that the app is publicly reachable,
   bypassing Cloudflare and the rate limits, and prints the exact `ports:`
   line to use instead. A container with no published port gets an explanation
   (publish one, or use `--network`). The script validates the input, writes
   `nginx/conf.d/app.<DOMAIN>.conf`, runs `nginx -t`, and reloads only if it
   passes (otherwise it rolls back). `--force` overwrites, `--dry-run` prints
   the config only.
3. **Commit** the new file (it contains no secrets) and check
   `https://app.<DOMAIN>`.

The generated `proxy_pass http://host.docker.internal:<port>;` is static
(`extra_hosts` is fixed when nginx starts), so `nginx -t` and nginx startup do
not depend on the app being up; requests return 502 until it is. Services that
run directly on the host work the same way; they must listen on the bridge IP
or `0.0.0.0` (loopback-only is not reachable from the container).

Notes on firewalls: Docker publishes ports through its own iptables rules, so
`ufw` rules do not filter them; binding to the bridge IP is the protection
here. `examples/app.example.conf` shows what the script generates.

### Alternative: shared proxy network

If you prefer container names, put the project on the `proxy` network and use
`--network`:

```sh
docker network connect proxy <container>      # or add the external `proxy` network in its compose file
scripts/add-site.sh app --network             # picker uses container-name:internal-port
scripts/add-site.sh app app:3000              # explicit
```

Names resolve at request time through Docker DNS, so nginx still starts if the
container is down. The catch: `docker network connect` is lost when the
container is recreated, unless the network is in its compose file.

## Main domain (apex)

`@` stands for the apex `<DOMAIN>` itself (the wildcard certificate already
covers it). The apex file is `nginx/conf.d/<DOMAIN>.conf`.

**Recommended: apex is canonical (no `www`)**

```sh
scripts/add-site.sh @ app:3000          # https://<DOMAIN> -> project
scripts/add-site.sh www --redirect @    # https://www.<DOMAIN>/x?y=1 -> 301 https://<DOMAIN>/x?y=1
```

**Alternative: `www` is canonical**

```sh
scripts/add-site.sh www app:3000
scripts/add-site.sh @ --redirect www
```

`--redirect <target>` works for any site and any target (a subdomain or `@`)
on ports 80 and 443, keeps the path and query string, takes no upstream, and
refuses a site that redirects to itself. A host has one file, so to change a
site from proxy to redirect (or back) re-run the command with `--force`.
Remove with `scripts/remove-site.sh @` / `remove-site.sh www`. Both DNS records
(apex and `www`) must exist; without a server block for a host, Cloudflare
shows error 525.

**Redirect loops:** never let two hosts redirect to each other (for example
`www --redirect @` together with `@ --redirect www`); browsers fail with
"too many redirects". `add-site.sh` refuses to write `X --redirect Y` while
`Y`'s file already redirects to `X`, unless you pass `--force`. Remove or
change the other file first (`--force` re-run or `remove-site.sh`).

**HSTS and redirects:** the port-80 redirect goes straight to the target
over HTTPS, so the source host (e.g. `www`) never receives a
`Strict-Transport-Security` header from port 80; the 443 redirect does send
it. That is fine because HSTS is sent without `includeSubDomains`, so each
host is covered only after the browser has itself seen it over HTTPS.

## Removing a project

```sh
scripts/remove-site.sh <subdomain|@>
```

Deletes the site file, runs `nginx -t`, reloads (restoring the file if the test
fails). The wildcard certificate is shared and is not touched.

## Certificate renewal

The `certbot` container runs `certbot renew` every 12 hours; certbot only
renews when the certificate is within 30 days of expiry and reuses the saved
Cloudflare credentials. Because certbot cannot signal the `nginx` container,
the nginx container acts as the deploy hook: it checks the checksum of
`live/wildcard/fullchain.pem` every minute and runs `nginx -s reload` as soon
as it changes. No Docker socket is shared. Test renewal with:

```sh
docker compose run --rm --entrypoint certbot certbot renew --dry-run
```

## Cloudflare proxy (orange cloud)

- Set the SSL/TLS mode to **Full (strict)**. The origin has a valid Let's
  Encrypt certificate, so strict validation works.
- `snippets/cloudflare-realip.conf` is included globally: connections from
  Cloudflare's ranges have their client address taken from `CF-Connecting-IP`,
  so logs and `X-Real-IP` / `X-Forwarded-For` show the real visitor. Requests
  from other addresses cannot spoof it.
- Cloudflare's ranges change rarely. Refresh them with
  `scripts/update-cloudflare-ips.sh` (fetches `ips-v4` / `ips-v6`, runs
  `nginx -t`, reloads, restores the old file on failure), then commit the
  diff. Run it now and then, or from cron (next section).
- WebSockets work through Cloudflare (enabled by default); use `--ws` on the
  sites that need them. Cloudflare's upload limit and 100 s proxy timeout still
  apply on the free plan.

### Weekly refresh of the Cloudflare ranges (cron)

`crontab -e` on the server (Mondays 04:15; use the real path of the checkout):

```cron
15 4 * * 1  cd /opt/nginx-proxy && scripts/update-cloudflare-ips.sh >> /var/log/cf-ips-update.log 2>&1
```

The script only reloads nginx when the ranges changed and the config
validates. Afterwards `git diff nginx/snippets/cloudflare-realip.conf` shows
what changed; commit it so the repo stays the source of truth.

### Firewall (optional)

To accept web traffic only from Cloudflare (so nobody can bypass it by hitting
the server IP), allow the Cloudflare ranges on 80/443 and nothing else. These
commands are documentation only; review them before running them yourself.
Keep SSH open first, or you will lock yourself out.

```sh
sudo ufw allow OpenSSH
for ip in $(curl -fsS https://www.cloudflare.com/ips-v4; echo; curl -fsS https://www.cloudflare.com/ips-v6); do
  sudo ufw allow proto tcp from "$ip" to any port 80,443
done
sudo ufw enable
```

**Docker caveat:** Docker publishes ports through its own iptables chains, which
are evaluated before ufw's rules, so the rules above may *not* restrict
`80/443` on the containers. To filter published ports you must put the rules
in the `DOCKER-USER` chain (for example with the `ufw-docker` approach) and
verify from an outside host that a non-Cloudflare address is refused. Also
re-apply the rules when the ranges change.

## Rate limits

Every generated site includes `snippets/rate-limit.conf`: per client IP (the
real IP, see above) 30 requests/s with a burst of 100, and at most 100
concurrent connections; excess requests get `429`. The zones (`req_per_ip`,
`conn_per_ip`) are defined in `nginx/nginx.conf`.

- **Tune for all sites**: change `rate=` in `nginx.conf`, or `burst` / the
  connection count in `rate-limit.conf`, then `nginx -t` and reload.
- **Tune or disable for one site**: in `nginx/conf.d/<host>.conf`, replace the
  `include .../rate-limit.conf;` line with your own `limit_req` / `limit_conn`
  lines, or delete it to disable limiting for that site.

## HSTS

`security-headers.conf` sends `Strict-Transport-Security: max-age=31536000`
for the host only. Add `includeSubDomains` (and later `preload`) in that
snippet only once every subdomain of the domain is served over HTTPS.

## Validation

```sh
docker compose config -q
docker compose run --rm --no-deps nginx nginx -t   # or: docker compose exec nginx nginx -t
shellcheck -x scripts/*.sh
```

Routing check without DNS:

```sh
curl -sI -H 'Host: app.<DOMAIN>' http://localhost/                      # 301 to https
curl -sk --resolve app.<DOMAIN>:443:127.0.0.1 https://app.<DOMAIN>/     # proxied content
curl -sI -H 'Host: unknown.<DOMAIN>' http://localhost/                  # connection closed (444)
```

## Troubleshooting

- **`cannot load certificate ... live/wildcard/fullchain.pem`**: the cert was
  not issued yet (run `scripts/init-cert.sh`), or `certbot/conf` was deleted.
- **certbot: "Unable to determine zone_id" / auth errors**: the token is wrong,
  or lacks `Zone → DNS → Edit` for this zone; check `secrets/cloudflare.ini`
  (mode 600, no quotes around the token).
- **certbot times out waiting for DNS**: raise
  `--dns-cloudflare-propagation-seconds` by passing it to `init-cert.sh`.
- **502 Bad Gateway**: upstream down, wrong port, or the container is not on
  the `proxy` network (`docker network inspect proxy`).
- **`host not found in upstream`** in `nginx -t`: a static upstream
  (`host.docker.internal` / IP) does not resolve; check `extra_hosts`.
- **Host service unreachable**: bind it to `0.0.0.0`/the bridge address and
  allow the Docker bridge in the host firewall (`ufw`).
- **Redirect loop behind Cloudflare**: SSL mode is "Flexible"; set it to
  "Full (strict)".
- **Logs**: `docker compose logs -f nginx`. Container logs are rotated by
  Docker (`json-file`, 5 files of 10 MB per service, set once in
  `docker-compose.yml`); change `max-size` / `max-file` there. Recreate the
  containers (`docker compose up -d`) for a change to apply.

## Secrets

`.env` and `.env.*` (except `.env.example`), everything in `secrets/` (except
`*.example`), `certbot/conf/` (certificates and keys), `*.pem`, `*.key` and
`logs/` are git-ignored. Never commit them.
